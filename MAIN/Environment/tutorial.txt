================================================================================
ACTION-RESPONSE DELAY EXPERIMENT -- COMMANDS
================================================================================

The experiment is a SEED STUDY: four conditions, five independent training runs
each. One run per condition could not tell whether a difference came from the
delay training or from the luck of that run -- two earlier sweeps disagreed with
each other by more than their own confidence intervals.

--------------------------------------------------------------------------------
LAYOUT
--------------------------------------------------------------------------------

    RUN EVERY COMMAND IN THIS FILE FROM THE MAIN FOLDER:

        cd thesis_Gijs/MAIN

    That is where the Environment, Training, Validation and Visualisation
    packages sit, so "python -m Training.train" and "python Validation/..."
    resolve. Running them one level up fails with
    "No module named 'Training'".

    thesis_Gijs/
      MAIN/                         <- run everything from here
        Environment/      the simulation: BlueSky, the airspace, the ATCO, the
                          rules, and this file
        Training/         train.py, one process per run
        Validation/       validation.py and create_plots.py, plus results/ and
                          figures/ once they have been produced
        Models/           trained runs land here, and this is where Validation
                          reads them from -- nothing is moved between phases
        Visualisation/    the live viewer and the seed-check renderer
      OLD/                superseded models and the report .tex sources, parked

    MAIN/Models/, MAIN/Validation/results/, MAIN/Validation/figures/ and OLD/
    are gitignored: they are regenerated by running the experiment, not by
    cloning. All four are created on demand, so deleting any of them is safe.

--------------------------------------------------------------------------------
THE SIX SEEDS
--------------------------------------------------------------------------------

    Everything is seeded from six numbers, all in Environment/config.py:

        TRAINING_SEEDS  = (1, 2, 3, 4, 5)     one per training run
        VALIDATION_SEED = 6                   the 100 held-out test scenarios

    A training seed fixes two things: the initial network weights (PPO(seed=S))
    and the sequence of scenarios the run flies (Random(S)). So the same seed in
    different conditions starts from the same weights and sees the same
    scenarios -- paired across conditions, independent across seeds.

    Each scenario seed then spins off three streams: the sector and initial
    traffic, the replacement traffic, and the delay draws. Replay a scenario
    seed and you get the same airspace AND the same delays.

    Training skips any scenario in the held-out set, so no model can ever meet a
    test scenario however long it runs. Between two runs of 300M steps
    (~250,000 episodes each, drawn from a pool of 1e9) about 60 scenarios are
    expected to appear in both by chance, 0.02% of the episodes. Within a single
    run about 30 scenarios repeat. Neither is worth engineering around.

    for i in range(400):
        if e.step(int(r.integers(0,10)))[3]: break
    s=e._ep_stats; print(m, 'transmitted', s['turns']+s['speeds'], 'executed', s['delay_acted'], 'discarded', s['discarded'])"

--------------------------------------------------------------------------------
ENVIRONMENT SETTINGS FOR THIS EXPERIMENT
--------------------------------------------------------------------------------

    rho                 1/20000 - 1/10000   sectors roughly 350-500 NM across
    exits_per_episode   4.0                 episode ends after 4 x n_ac exits
    max_crossings       8.0                 step cap, in case traffic stops leaving.
                                            Measured headroom is 4-5x, so it never
                                            binds in a healthy episode
    spawn rejection     > 15 NM to any aircraft AND no predicted LoS (t_los)
                        inside the 360 s horizon
    R_los               scales with the SECONDS of lost separation in the step,
                        0 to -5, not one flat penalty per step
    advisory delays     redrawn on every revision at kappa = 0.7 of a full
                        response time, measured from the moment of revision;
                        repeating the advice already standing costs workload but
                        does not restart the assessment

    Results from before these settings are not comparable with results after.
    The runs parked in OLD/ predate all of it.

    # One environment per run, which is the default: BlueSky is a
    # process-global singleton, so two envs in one process would share one
    # simulation. Parallelism comes from the 20 processes, not from vectorising
    # inside a run. PPO's rollout is therefore 4096, and it must be the same for
    # all 20 runs.

    # FLORIS2 has 12 cores. Twenty runs will not all get a core, so expect them
    # to progress at different rates -- which is exactly why they must be
    # stopped by step count, not by clock time.

    # 300M is a CEILING, not a target. Stop the runs by hand once the reward
    # curve has settled; Ctrl-C saves final_model through the finally block,
    # kill -9 does not. Stop all 20 at the SAME STEP COUNT, not at the same time
    # of day, or the comparison measures the budget instead of the delay. Write
    # down where each run stopped.

--------------------------------------------------------------------------------
IS IT STILL LEARNING?
--------------------------------------------------------------------------------

    NOTHING STOPS A RUN BY ITSELF. There is no early stopping and no patience
    counter: every callback only writes to TensorBoard, and each one returns
    True unconditionally. A run ends when you press Ctrl-C, or when it reaches
    the --timesteps ceiling. The metrics below are evidence for that decision,
    not a rule that acts on its own.

    episode/reward_slope_per_1M   The one metric added for this. Least-squares
                                  slope of the episode reward over the last 200
                                  episodes, as reward gained per million steps.
                                  Positive means the reward is still climbing;
                                  wandering either side of zero means it has
                                  stopped climbing over that window.

    SB3 logs the rest for free under train/, and they say whether the slope can
    be trusted:

    train/explained_variance      Climbs toward 1.0 while the critic is learning.
                                  Near zero late in a run means the advantages
                                  are noise, so a flat slope says nothing.
    train/approx_kl               How far each update moves the policy. Small
                                  and shrinking is healthy; spikes mean the run
                                  is still unstable.
    train/clip_fraction           Large early, then small and steady.

    advisory/*                    What the policy actually issues. A reward
                                  curve can flatten because the policy gave up
                                  and issues almost nothing, which looks the same
                                  as convergence on the reward curve alone.

    Whatever you decide, the comparison only holds if every run is stopped at
    the SAME STEP COUNT, not at the same wall-clock time -- the 20 runs share 12
    cores and will not reach a given step count together. Write down where each
    run stopped.
