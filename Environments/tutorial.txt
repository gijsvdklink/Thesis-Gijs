================================================================================
ACTION-RESPONSE DELAY EXPERIMENT -- HOW TO RUN IT
================================================================================

THE QUESTION
    How does an air traffic controller policy change when pilots do not comply
    instantly, and does the SHAPE of the delay distribution matter, or only its
    mean?

THE FOUR ARMS
    All three delayed arms have the SAME mean response time, 30 s / 15 s, and
    none of them has a ceiling. They differ only in shape, which is the
    experimental variable.

    none            0 s.  The baseline: pilots comply immediately.

    deterministic   Exactly 30 s for the first advisory to a focus ship, exactly
                    15 s once that pilot has executed one. No randomness, so the
                    controller could count down to the exact second.

    lognormal       Random, mean 30 s / 15 s, sigma 0.4, unbounded. Mass
                    concentrated near the mean: a long silence means a response
                    is overdue, so waiting is informative. The delay is drawn
                    ONCE at issue time and held as hidden state -- the agent
                    sees that something is pending and how long it has waited,
                    never when it will land.

    probabilistic   The Markov chain. Each simulated second the pilot either
                    stays in "not executed" (29/30, or 14/15 once engaged) or
                    acts. No forced response, so the tail is unbounded and a
                    delay past 120 s is rare but possible. Memoryless: how long
                    the pilot has already been silent tells the controller
                    nothing about when they will act, and an immediate response
                    is always on the table.
                    Implementation note: the code samples the equivalent
                    geometric delay once at issue rather than rolling a die each
                    second. Identical distribution -- the per-second chance
                    cannot change while an instruction is outstanding.

ENGAGEMENT ("has the pilot already executed an advisory?")
    Identical in all four arms. It is FALSE every time the focus moves to a new
    aircraft. It becomes TRUE the moment an advisory to that aircraft executes,
    and stays true for as long as that aircraft keeps the focus. Only then does
    the faster 15 s / (1/15) branch apply.

    Watch delay/engaged_branch_frac in TensorBoard: it is the fraction of
    advisories that took the faster branch.

--------------------------------------------------------------------------------
BEFORE TRAINING -- CHECK THE PLUMBING
--------------------------------------------------------------------------------

    python -m Environments.v4.test_delays
        Checks the delay models on their own: means, tails, memorylessness,
        reproducibility. Takes about 20 s. Should end "all checks passed".

    python -m Validation.delay_diagnostics --episodes 2 --steps 600
        Runs all four arms and prints:
          - whether the arms see IDENTICAL scenarios at the same seed
          - the realised delay histogram per arm
          - how often the faster engagement branch fires
          - the KPIs the arms are compared on
        Add --model <best_model.zip> to run a trained policy instead of random
        actions.

--------------------------------------------------------------------------------
THE EXPERIMENT -- FIVE TERMINALS
--------------------------------------------------------------------------------

Each arm gets its own process. --n-envs is how many cores that arm uses. Use the
SAME --seed everywhere: that is what makes the arms share their scenarios.

    # terminal 1 -- baseline, no delay
    python -m Training.v4_train --delay none          --seed 0 --n-envs 2

    # terminal 2 -- deterministic 30 s / 15 s
    python -m Training.v4_train --delay deterministic --seed 0 --n-envs 2

    # terminal 3 -- log-normal, mean 30 s / 15 s
    python -m Training.v4_train --delay lognormal     --seed 0 --n-envs 2

    # terminal 4 -- probabilistic, 1/30 (1/15) per second, Markov chain
    python -m Training.v4_train --delay probabilistic --seed 0 --n-envs 2

    # terminal 5 -- TensorBoard
    tensorboard --logdir Runs_saved/experiments --port 6006

Defaults: 50,000,000 timesteps, 2 envs, evaluation every 100,000 steps on five
fixed held-out scenarios (~12% overhead). Override with --timesteps,
--eval-every and --eval-episodes. Push --eval-every much below 100,000 and the
evaluation starts costing more than the training it interrupts; drop
--eval-episodes first if you need points closer together than that.

    # short smoke run before committing to the full budget
    python -m Training.v4_train --delay probabilistic --timesteps 200000

--------------------------------------------------------------------------------
WHAT TO LOOK AT IN TENSORBOARD
--------------------------------------------------------------------------------

Six tags, deliberately. Anything that barely moved between arms was dropped;
Validation/delay_diagnostics.py still reports the rest when you want them.

    safety/los_events_per_flight_hour
        THE safety number. Separation losses per flight hour. Episodes differ in
        aircraft count, sector size and length, so a raw LoS count is not
        comparable between them -- this is.

    route/exit_deviation_nm
        How far from its planned exit point an aircraft actually left the
        sector: the lateral displacement the avoidance cost.

    route/arrival_rate
        Fraction that left on their route heading rather than still sitting in
        an avoidance turn.

        BOTH ROUTE METRICS ARE SCORED OVER MANOEUVRED AIRCRAFT ONLY. Only one
        aircraft is controlled per step, so ~80% of traffic crosses untouched
        and exits perfectly on route. Including it pushed the arrival rate to
        ~91% and the deviation to ~21 NM regardless of policy -- it was
        measuring how many aircraft were ignored. Over manoeuvred aircraft the
        same episode reads 55% and 74 NM, which actually responds to the policy.

    delay/mean_response_s
        The delay pilots actually received, as opposed to the nominal 30/15.

    delay/instructions_discarded
        Advisories replaced before the pilot could act on them. The agent paid
        for those radio calls but they never flew. By design, but worth knowing:
        it runs to several hundred per episode.

    episode/reward_total

        NOTE ON THE X-AXIS: it counts individual environment steps, summed over
        the parallel workers -- not episodes. One step is one advisory decision
        and 5 s of simulated time. The plotted value is the sum of rewards over
        a whole episode, recorded at the step the episode ended.

        One episode is 2,100-4,800 steps, i.e. 3.0-6.6 hours of simulated
        traffic and 45-200 aircraft-flight-hours. A 50M-step arm is therefore
        roughly 12,000-24,000 episodes.

        The eval/ curves are the same metrics measured with a DETERMINISTIC
        policy on fixed held-out scenarios. Expect them above the training
        curves, which include exploratory actions.

--------------------------------------------------------------------------------
AFTER TRAINING
--------------------------------------------------------------------------------

    python -m Validation.cross_evaluate --runs Runs_saved/experiments --episodes 10
    tensorboard --logdir Runs_saved/cross_eval
        Trains under one condition, tests under another: a 4x4 grid. Answers
        what happens to a policy that assumed instant compliance when it meets
        pilots who take 30 s. Read the baseline row with care -- see the caveat
        in the script's header.

    python -m Validation.mc_evaluate --model <path>/best_model.zip --episodes 30
        Monte-Carlo sweep over aircraft count and density.

    python figures/plot_delays.py
        Regenerates figures/delays.png, the three delay distributions. It samples
        delays.py directly, so it cannot drift out of sync with the environment.

RANDOMNESS
    Each episode derives three independent generators from one seed: one for the
    scenario (sector, aircraft count, density, initial traffic), one for
    replacement aircraft, one for the response delays. Keeping them apart is
    what lets the arms share scenarios -- if the delay draws came from the same
    stream, every random decision after the first advisory would shift, and the
    arms would be training on different traffic.

    Worker w, episode k always lands on the same scenario in every arm, as long
    as the arms are launched with the same --seed. What happens after that
    depends on the policy and diverges by design.
